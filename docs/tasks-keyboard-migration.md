# Перенос команд бота на кнопки: задачи

Цель: все действия, которые сейчас вызываются командами вида `/report` или `/set_plan 12695650 50000000`, должны быть доступны с клавиатуры Telegram. Команды при этом продолжают работать. Ни одна функция не теряется и не меняет поведение.

Статус: план. Ничего из перечисленного ещё не сделано.

---

## 1. Инварианты

Это то, что проверяется в каждой задаче при приёмке.

1. **Кнопка вызывает тот же код, что и команда.** Никакой логики в обработчике кнопки, только разбор нажатия и вызов существующей функции. Иначе появятся две версии одного действия.
2. **Команды не удаляются.** Все `bot.onText` остаются. Кнопки добавляются сверху.
3. **Права не ослабляются.** Проверка роли выполняется в функции действия, а не при построении клавиатуры. Скрытая кнопка не защита: пользователь может отправить текст кнопки руками или старый callback.
4. **Опасные действия требуют подтверждения.** Остановка Феникса, удаление команды, снятие админа, исключение из рейтинга, смена роли.
5. **Текущие диалоги не ломаются.** Нажатие кнопки меню во время ввода дат, кода активации или AI-сессии не должно уйти в этот диалог как текст.
6. **Отчёты отправляются теми же функциями.** HTML-разметка, Excel-файл и разбиение длинных сообщений сохраняются.

## 2. Инвентарь команд и целевой элемент интерфейса

Условные обозначения элементов:
- **Кнопка** — прямое действие без аргументов.
- **Выбор** — inline-список вариантов (менеджеры, месяцы, команды, периоды).
- **Ввод** — бот просит значение следующим сообщением, с кнопкой «Отмена».
- **Подтверждение** — inline «Да / Нет» перед выполнением.
- **Команда** — остаётся только командой, в меню не выносится.

## 3. Архитектура решения

Коротко, чтобы задачи ниже читались одинаково.

**Два слоя клавиатур.**
- **Reply-клавиатура** (постоянная, внизу экрана) — главное меню по роли: разделы «Отчёты», «AI-murabbiy», «Команда», «Компания», «Феникс», «Пользователи», «Помощь». Она шлёт обычный текст, поэтому её нажатия приходят в `bot.on("message")`.
- **Inline-клавиатуры** (под сообщением) — содержимое раздела и все выборы. Они шлют `callback_data`, не больше 64 байт.

**Реестр действий.** Один модуль `src/bot/actions/registry.ts`: у каждого действия есть идентификатор, роли, которым оно доступно, и функция выполнения. Команды и кнопки указывают на один и тот же идентификатор. Это единственный источник правды для меню и для `/help`.

**Маршрутизатор текста кнопок.** В начале `bot.on("message")`, до разбора состояний, точное сравнение текста с реестром подписей кнопок. Совпало — выполняем действие и выходим. Не совпало — текущая логика без изменений.

**Пространство имён callback.** Новые кнопки используют префикс `m:` (`m:<action>[:<arg>]`). Уже занятые префиксы: `tl_manage:`, `tl_card:`, `tl_ask:`, `rop_*`, `admin_delete_team_*`, `phx:` и токены карточек задач. Каждый из четырёх существующих обработчиков `callback_query` игнорирует чужие префиксы, новый обработчик делает так же.

**Ожидание ввода.** Одна таблица состояний «бот ждёт значение» с типом ожидания, сроком жизни и кнопкой «Отмена». Хранится в Redis, а не в памяти процесса: сейчас пять состояний живут в `Map` и теряются при каждом деплое на Railway.

## 4. Задачи

Размер: S — до половины дня, M — день-два, L — больше двух дней. Зависимости указаны номерами.

### Этап 0. Подготовка

**T1. Единая проверка ролей.** `isAdmin` реализован четыре раза ([index.ts](../src/bot/index.ts), [adminRoles.ts](../src/bot/handlers/adminRoles.ts), [performance.ts](../src/bot/handlers/performance.ts), [rop.ts](../src/bot/handlers/rop.ts)), проверки РОПа и тимлида тоже разбросаны. Вынести в `src/bot/access.ts` функцию, которая по Telegram ID возвращает набор ролей: `admin`, `rop`, `teamlead`, `manager`, `unlinked`. Учесть случай «админ и одновременно привязанный менеджер»: сейчас `/report` для него показывает отчёт менеджера, а не админский. Это поведение сохранить и задокументировать.
Приёмка: все существующие проверки используют новый модуль, поведение команд не изменилось. Размер M.

**T2. Реестр действий.** Создать реестр из раздела 3. Перенести тела всех `bot.onText` в именованные функции с сигнатурой `(ctx: { chatId, userId, roles, args }) => Promise<void>`. Сами `bot.onText` остаются и вызывают функции из реестра. Файл [index.ts](../src/bot/index.ts) на 1868 строк при этом разбить по разделам: `handlers/reports.ts`, `handlers/aiCoach.ts`, `handlers/admin.ts`.
Приёмка: каждая команда из раздела 2 есть в реестре; мета-тест проверяет, что у каждого `bot.onText` есть запись в реестре или явная пометка «только команда». Размер L. Зависит от T1.

**T3. Меню команд Telegram.** Вызвать `setMyCommands` с описаниями по областям: для каждого привязанного чата свой набор по роли. Это даёт подсказки при вводе «/» и не требует клавиатур. Обновлять при `/start` и после смены роли.
Приёмка: в поле ввода у менеджера, тимлида, РОПа и админа видны только их команды. Размер S. Зависит от T1.

### Этап 1. Каркас клавиатур

**T4. Главное меню по роли.** Модуль `src/bot/keyboards/mainMenu.ts`: строит reply-клавиатуру из реестра по набору ролей. Показывать при `/start`, по кнопке «Помощь», после смены роли и после привязки кода. Для непривязанного пользователя клавиатуры нет, только просьба ввести код. Параметры: `resize_keyboard`, `is_persistent`.
Приёмка: у каждой роли свой набор разделов, скриншоты четырёх ролей приложены к задаче. Размер M. Зависит от T2.

**T5. Маршрутизатор текста кнопок.** В `bot.on("message")` до всех состояний: точное совпадение текста с подписями из реестра. Подписи не должны совпадать с возможным вводом: шестизначный код, дата `ДД.ММ.ГГГГ`, число, свободный вопрос. Все подписи начинаются с символа-маркера или содержат пробел и буквы, чтобы это гарантировать. Тест на уникальность подписей и на отсутствие совпадений с шаблонами ввода.
Приёмка: нажатие любой кнопки меню во время ввода дат, кода или AI-сессии выполняет действие кнопки, а состояние диалога остаётся как было, как это сейчас происходит при вводе команды. Снимает состояние только кнопка «Отмена». Размер M. Зависит от T4.

**T6. Обработчик inline-кнопок меню.** Один `bot.on("callback_query")` для префикса `m:`. Разбор `m:<action>[:<arg>]`, проверка роли, вызов действия из реестра, `answerCallbackQuery` ровно один раз, дедупликация по `query.id` через тот же Redis-ключ, что и `claimUpdate`. При выполнении убирать кнопки с сообщения, как уже сделано для `phx:`.
Приёмка: повторное нажатие уже обработанной кнопки даёт короткий ответ «Уже выполнено» и ничего не делает. Размер M. Зависит от T2.

**T7. Ожидание ввода в Redis.** Модуль `src/bot/pendingInput.ts`: `expect(userId, kind, payload, ttl)`, `take(userId)`, `cancel(userId)`. Срок жизни 10 минут. Кнопка «Отмена» как inline под запросом и как подпись в reply-клавиатуре. Перевести на него `periodState`; остальные состояния (`aiSessions`, `supervisorAiSessions`, `roleFlowState`, `teamLeadManageFlowState`) перевести отдельной задачей T14, чтобы не смешивать.
Приёмка: ввод переживает перезапуск сервиса; просроченный ввод отвечает «время вышло, нажмите кнопку снова». Размер M. Зависит от T5.

### Этап 2. Разделы меню

Каждая задача этого этапа: кнопки раздела, нужные выборы и вводы, подтверждения, обновление `/help`, тесты маршрутизации. Приёмка одинаковая: каждое действие раздела выполняется с кнопки и даёт тот же результат, что команда; проверено вручную по чек-листу из раздела 2 для соответствующей роли.

**T8. Раздел «Отчёты» и «AI-murabbiy».** `/report`, `/week`, `/month`, `/period`, `/errors`, `/my_stats`, `/deal` через ввод ID, `/ask*` через выбор периода, `/stop_ai` как динамическая кнопка. Для админа без привязки отчёты идут в админском режиме, как сейчас. Размер M. Зависит от T6, T7.

**T9. Раздел «Команда» для тимлида.** Прямые кнопки плюс вход в существующие потоки `tl_manage:`, `tl_card:`, `tl_ask:`. Существующие потоки не переписывать. Размер S. Зависит от T6.

**T10. Раздел «Компания» для РОПа и админа.** Прямые кнопки плюс вход в потоки `rop_*`. Размер S. Зависит от T6.

**T11. Планы, рейтинг, статус звонков.** `/set_plan` как цепочка «менеджер, сумма, месяц» с общим компонентом выбора менеджера (постранично, по 8, с поиском по первым буквам), `/plans` с выбором месяца, `/rating_*` с подтверждением, `/call_status` с выбором дней, `/sync_stages`. Компонент выбора менеджера переиспользуется в T12 и T13. Размер L. Зависит от T6, T7.

**T12. Раздел «Феникс».** Статус, переключатель, лимит одним экраном с двумя кнопками, `/inactivity_on` через существующее подтверждение `phx:`, `/inactivity_off` с подтверждением, `/inactivity_lead` через ввод ID. Размер M. Зависит от T6, T7.

**T13. Раздел «Пользователи» и «Синхронизация» для админа.** Списки, сброс кода с подтверждением, добавление и снятие админа, роли и команды через выборы, `/analyze_deal` через ввод, `/delete_team` через существующее подтверждение, кнопка «Указать срок» на карточке AI-задачи вместо ручного ввода токена для `/call_task_time`. Отладочные команды остаются командами и перечисляются в `/help` отдельным блоком. Размер L. Зависит от T6, T7, T11.

### Этап 3. Доводка

**T14. Остальные состояния в Redis.** Перевести `aiSessions`, `supervisorAiSessions`, `roleFlowState`, `teamLeadManageFlowState` на хранилище из T7 с сохранением их сроков жизни и семантики. История AI-сессии может быть большой: хранить её так же, как сейчас хранится в БД для `/coach`, а в Redis держать только указатель. Размер M. Зависит от T7.

**T15. Помощь и документация.** `/help` генерируется из реестра: сначала разделы и кнопки, затем команды с аргументами. Обновить [admin-commands.md](admin-commands.md): для каждой команды указать путь кнопками. Размер S. Зависит от T8–T13.

**T16. Тесты.** Сейчас обработчики бота тестами не покрыты, кроме карточек задач и стартовых проверок. Добавить: мета-тест полноты реестра (T2), уникальность подписей и префиксов callback (T5, T6), состав меню по ролям в виде снимков (T4), проверка прав для каждого действия при вызове с чужой ролью (T1), сценарии ожидания ввода с истечением срока (T7). Тесты пишутся вместе с соответствующими задачами, эта задача закрывает пропуски. Размер M.

**T17. Выкат и откат.** Флаг окружения `BOT_KEYBOARDS_ENABLED`. Порядок: админы, затем РОП и тимлиды, затем менеджеры. Логировать, что нажато: действие, роль, источник (команда или кнопка), без текста сообщений. Откат: выключить флаг и отправить `remove_keyboard` при следующем `/start`. Размер S. Зависит от T4.

## 5. Риски и как они закрываются

| Риск | Чем закрыт |
|---|---|
| Текст кнопки уходит в активный диалог как ввод | T5: маршрутизатор до состояний, запрет подписей, похожих на ввод, тест |
| Кнопка обходит проверку прав | Инвариант 3, T1, тест вызова с чужой ролью в T16 |
| Двойное нажатие inline-кнопки выполняет действие дважды | T6: дедупликация по `query.id`, снятие кнопок после выполнения |
| Состояния теряются при деплое | T7, T14: Redis |
| `callback_data` длиннее 64 байт | T6: только идентификаторы и числовые аргументы, строки через ожидание ввода |
| Новый обработчик `callback_query` перехватывает чужие нажатия | Префикс `m:`, тест уникальности префиксов |
| Расхождение между кнопками, командами и `/help` | Реестр как единственный источник, `/help` генерируется |
| Один файл на 1868 строк становится ещё больше | T2: разбиение по разделам до добавления кнопок |

## 6. Что не меняется

- Поведение команд и их аргументы.
- Форматы отчётов, HTML-разметка, Excel-файл, разбиение длинных сообщений.
- Существующие inline-потоки тимлида, РОПа, удаления команды, подтверждения Феникса и карточек AI-задач. К ним добавляется только вход с кнопки.
- Уведомления админам и их аудитория.
- Телефонные и amoCRM-части проекта. Задачи касаются только `src/bot`.

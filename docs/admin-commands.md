# Новые команды и режимы админки

Справочник по тому, что добавилось поверх существующего бота: справочник по сделке, отчёты по звонкам/поступлениям/плану, планы продаж, автозаполнение полей amoCRM и бэкап списков вариантов.

Существующие команды (`/report`, `/week`, `/errors`, `/ask`, `/teams`, `/set_role` и прочие) не менялись.

---

## 1. Справочник по сделке

| Команда | Кому |
|---|---|
| `/deal <ID сделки>` | всем авторизованным, с ограничением по ролям |
| просто число в чат | то же самое |

Голый номер обрабатывается **последним** в цепочке обработчиков: если вы вводите код активации, дату для `/period` или общаетесь с AI-коучем, число уйдёт туда, а не в справочник.

**Что показывает:** воронку и стадию, клиента с телефоном, ссылку в amoCRM, число звонков и среднюю оценку, повторяющиеся ошибки с частотой, рекомендации ИИ из последнего звонка, где они есть, и историю звонков с оценками.

```
🗂 Bitim #26062823
👤 Aziza · 998901234567
📂 Voronka: UZUM · Bosqich: 58160726
🔗 https://qadamsales.amocrm.ru/leads/detail/26062823

📞 Qo'ng'iroqlar: 3 · ⭐ O'rtacha ball: 72/100

⚠️ Takrorlangan xatolar:
• Ehtiyoj ochilmadi (3×)
• Narx aytilmadi

🤖 Mijoz bo'yicha keyingi qadamlar:
• Juma kuni qayta qo'ng'iroq qiling

🕘 Qo'ng'iroqlar tarixi:
• 12.08 14:30 · 8d 32s · 72/100 · Aziza
```

**Доступ:**

| Роль | Какие сделки видит |
|---|---|
| Админ | любые |
| РОП | любые |
| Тимлид | где есть звонок его команды |
| Менеджер | где есть его собственный звонок |

Чужая сделка отвечает «не найдена», а не «нет доступа»: иначе ответ подтверждал бы, что такая сделка существует.

## 2. Отчёты: звонки, поступления, план

| Команда | Кому | Что показывает |
|---|---|---|
| `/my_stats` | всем авторизованным | свой отчёт за вчера |
| `/team_stats` | тимлид | свою команду |
| `/team_stats` | РОП, админ | всю компанию |

```
📊 Kecha (29.08) — Aziza

📞 Qo'ng'iroqlar: 47 (dozvon: 31 · nedozvon: 16)
⏱ Suhbat vaqti: 3s 20d
⭐ O'rtacha ball: 72/100 (6 ta tahlil)

💰 Tushumlar:
• Muvaffaqiyatli: 3 ta · 12 500 000
• Qisman to'langan: 2 ta · 1 800 000

🎯 Oylik reja: 50 000 000
✅ Bajarildi: 32 000 000 (64%)
📉 Qoldi: 18 000 000
```

Командный отчёт добавляет строку по каждому менеджеру, отсортированную по выручке:

```
👤 Menejerlar:
• Aziza: 31/47 dozvon · ⭐ 72/100 · 💰 12 500 000 · reja 64%
• Muslima: 12/22 dozvon · ⭐ 61/100 · 💰 4 000 000 · reja 13%
```

### Откуда берутся цифры

| Блок | Источник |
|---|---|
| Звонки, дозвон/недозвон | история OnlinePBX за период |
| Средняя оценка | проанализированные звонки в БД (только длиннее 6 минут) |
| Поступления | журнал переходов сделок в оплаченные стадии |
| План | таблица `SalesPlan` |

**Дозвон** определяется по `user_talk_time > 0` — звонок, который прозвонил и сорвался, имеет длительность, но нулевое время разговора.

**Средний балл команды взвешен по числу звонков**, а не как среднее от средних: менеджер с одним звонком не весит столько же, сколько с девятью.

### Предупреждения в отчёте

| Строка | Значение |
|---|---|
| `⚠️ Qo'ng'iroqlar soni to'liq bo'lmasligi mumkin` | день упёрся в лимит страницы истории PBX, число звонков может быть занижено |
| `⚠️ Summasi aniqlanmagan bitimlar: N` | оплаты записаны, но сумма не определена — не настроено `AMOCRM_PAYMENT_AMOUNT_FIELD_ID` |
| `⭐ O'rtacha ball: tahlil qilingan qo'ng'iroq yo'q` | за период не было звонков длиннее 6 минут |
| `🎯 Oylik reja: belgilanmagan` | план на этот месяц не поставлен |

Эти же блоки добавлены в **ежедневный отчёт менеджерам в 09:00** — он теперь содержит звонки, поступления и план, а не только оценки.

## 3. Планы продаж

| Команда | Кому |
|---|---|
| `/set_plan <amoCRM ID> <сумма> [YYYY-MM]` | РОП, админ |
| `/plans [YYYY-MM]` | РОП, админ |

```
/set_plan 12695650 50000000          → план на текущий месяц
/set_plan 12695650 50 000 000        → пробелы в сумме допустимы
/set_plan 12695650 50000000 2026-09  → план на конкретный месяц
```

План ставится **на менеджера на месяц, в сумме**. План команды — сумма планов её участников, отдельно он не задаётся.

Месяц определяется по календарю Алматы, не по UTC: 31 августа в 20:00 UTC — это уже сентябрь.

Отклоняются: `0`, отрицательные, дробные, `50млн`, суммы больше 100 млрд. Это защита от опечатки, а не от больших планов.

**Прогресс плана считается только по «Успешно реализовано».** Частично оплаченные показаны отдельной строкой и план не двигают — иначе сделка с предоплатой засчиталась бы дважды.

## 4. Автозаполнение полей при автопереводе этапа

Когда роутер видит целевой этап, но amoCRM блокирует перевод незаполненными обязательными полями, поля заполняются автоматически и сделка едет дальше.

| Тип поля в amoCRM | Что происходит |
|---|---|
| `text`, `textarea`, `numeric`, `price`, `monetary` | пишется текст от ИИ |
| `select`, `radiobutton`, `multiselect` | ищется подходящий существующий вариант; если нет — создаётся новый **вариант внутри поля** |
| `date`, `checkbox`, `file` и прочие | заполнить нельзя — перевод блокируется |

Само поле никогда не создаётся, только вариант внутри существующего.

Список обязательных полей берётся из живого `required_statuses` amoCRM для конкретного целевого этапа — при изменении настроек в CRM код подхватит их сам.

### Включение

```bash
AMOCRM_CALL_STAGE_AUTOFILL_ENABLED=true
AMOCRM_CALL_STAGE_AUTOMATION_EXECUTION_MODE=live   # обязательно
```

Выключено по умолчанию и намеренно отделено от флага роутера: роутер только двигает этапы, а автозаполнение пишет данные в CRM и меняет списки вариантов. При `EXECUTION_MODE=dry_run` включение отклоняется с ошибкой при старте.

### Правила, из-за которых перевод может не состояться

- **Всё или ничего.** Если хотя бы одно поле заполнить нельзя, не пишется ничего: частичная запись оставила бы выдуманные значения и всё равно не разблокировала перевод.
- **Неоднозначный вариант.** Если значение одинаково подходит к нескольким существующим вариантам («Toshkent shahri» при наличии и «Toshkent», и «Toshkent viloyati»), система не выбирает, а блокирует и присылает список конкурентов.
- **Поле-предохранитель.** У «Sdelkani dubl bormi» значение `Yoq` жёстко задано, ИИ о нём не спрашивают, и вариант для него не создаётся никогда.
- **Нет журнала вариантов.** Если не удалось сохранить исходный список вариантов поля, вариант не создаётся.

### Сопоставление вариантов

Порядок: точное совпадение → синоним → неоднозначность → создать новый.

| Правило | Пример |
|---|---|
| Регистр, пунктуация, апостроф | `FARG'ONA` = `Fargʻona` |
| Кириллица и латиница | `Самарканд` = `Samarqand` |
| Уточняющие слова | `Toshkent shahri` → `Toshkent`, `Excel kursi` → `Excel` |
| Опечатки | `Samarqannd` → `Samarqand` |

Слова `viloyati` и `tumani` **не отбрасываются** — это другие места, а не уточнение города. Опечатки не ищутся в значениях короче 6 символов: `SMM` и `SEO` иначе слились бы.

### Лог админам

Приходит на каждый автоперевод с автозаполнением:

```
Проверка автоперевода UZUM
Сделка: #26062823 — https://qadamsales.amocrm.ru/leads/detail/26062823
Целевой этап: квалифицирован
Обязательные поля заполнены автоматически, сделка передвинута.
Заполнено полей: 10 (предположений ИИ: 4, новых вариантов списка: 1)

• Jinsi: Ayol (из разговора)
• Region: Samarqand (⚠️ предположение ИИ, ⚠️ создан новый вариант списка)
• Kurs: Excel (из разговора, сопоставлено с существующим вариантом, ИИ сказал «Excel kursi»)
```

| Пометка | Значение |
|---|---|
| `из разговора` | значение подтверждается транскриптом |
| `⚠️ предположение ИИ` | в разговоре этого не было, модель предположила |
| `⚠️ создан новый вариант списка` | в поле добавлен новый вариант, он виден всем менеджерам |
| `сопоставлено с существующим вариантом` | использован готовый вариант, в скобках — как сказал ИИ |

Отдельные типы сообщений: `Автозаполнение не выполнено` (с причиной, сделка не передвинута) и `Поля заполнены автоматически, но сделка НЕ передвинута`.

## 5. Бэкап списков вариантов

**Автоматически в 09:00 и 21:00** всем админам приходит файл `amo-field-options-2026-08-30-0900.txt`. Файлом, а не сообщением — длинный список не упирается в лимит Telegram.

Внутри по каждому полю: исходный список с ID и значениями, затем что добавил ИИ и когда. Отдельным блоком — добавления без исходного снимка.

```
Поле: Region (id 967019, тип select)
Исходный список сохранён: 28.08.2026 10:00

ИСХОДНЫЕ ВАРИАНТЫ (2):
  1	Toshkent
  2	Samarqand

ДОБАВЛЕНО ИИ (1):
  3	Andijon	29.08.2026 11:30
```

Исходный список сохраняется **один раз на поле, перед первым изменением**, и больше никогда не перезаписывается. Для полей, которых ИИ ещё не касался, снимка нет — первый бэкап после деплоя будет почти пустым.

### Откат добавленных вариантов

```bash
npm run amo-options:rollback                    # сухой прогон: печатает план
npm run amo-options:rollback 967019             # только одно поле

AMO_FIELD_OPTION_ROLLBACK_CONFIRM=remove_ai_added_options \
  npm run amo-options:rollback                  # применить
```

Удаляются **только варианты из журнала**. Варианты, которые люди добавили руками после снимка, сохраняются — полное восстановление снимка снесло бы их. Сам снимок остаётся в БД и печатается в отчёте, если понадобится ручное восстановление.

## 6. Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `AMOCRM_CALL_STAGE_AUTOFILL_ENABLED` | автозаполнение обязательных полей | `false` |
| `AMOCRM_PAYMENT_AMOUNT_FIELD_ID` | ID поля с фактической суммой оплаты | не задано |
| `AMO_FIELD_OPTION_ROLLBACK_CONFIRM` | подтверждение отката вариантов | не задано |

Без `AMOCRM_PAYMENT_AMOUNT_FIELD_ID` частично оплаченные сделки записываются, но **без суммы**: в отчёте видно количество, а в деньгах ноль и предупреждение. Бюджет сделки вместо фактического платежа не подставляется — это завысило бы выручку.

## 7. Что требует настройки

- **ID стадий «Часть оплачена»** по воронкам кроме UZUM — в `src/services/salesRevenuePolicy.ts` сейчас только `6909890 → 58810350`.
- **ID поля с суммой оплаты** — в `AMOCRM_PAYMENT_AMOUNT_FIELD_ID`.

Поступления начинают накапливаться с момента деплоя: вебхук фиксирует только новые переходы, исторических данных не будет.
